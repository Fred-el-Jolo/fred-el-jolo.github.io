TL;DR

  • 4× Raspberry Pi 4 (8GB) running k3s — a featherweight Kubernetes.
  • Boots from SSD over USB, not SD cards. This is the single biggest reliability win.
  • Total spend ~€420; idle draw under 20W for the whole rack.
  • Uptime since the last reboot: 148 days. It just sits there and works.

For years I rented a VPS for the handful of small services I self-host. It worked, but it never felt like mine — and the monthly bill quietly crept up. The Pi cluster started as a curiosity and ended up replacing the VPS entirely. It has been more reliable than I had any right to expect.

Note

This assumes some comfort with the Linux command line. If ssh and systemctl are familiar, you are ready for everything below.

The parts list

Resist the urge to cheap out on power and storage — they are where flaky clusters are born. Here is exactly what I bought, and what each piece is for.

ComponentChoiceQtyWhy
BoardRaspberry Pi 4 (8GB)4Headroom for memory-hungry pods

Network8-port gigabit switch1Wired only — Wi-Fi is for laptops
CaseStackable acrylic + fans1Airflow under sustained load

The acrylic case matters more than it looks. Under a real Kubernetes workload the boards throttle without active cooling, and a throttled node is a node that drops out of the cluster at the worst moment. Two 40mm fans kept every board below 60°C even during a full rebuild.

Cabling is the part that turns a pile of boards into something you are happy to look at every day. Short, identical Ethernet runs and a single power feed do most of the visual work. Label both ends of every cable — future-you will be grateful.

Flashing the boards

Skip the SD card entirely. Booting from SSD over USB 3 is faster, and — far more importantly — it survives. SD cards wear out under the constant small writes that container logs produce.

Write the image

Use the official imager to write Raspberry Pi OS Lite (64-bit) to each SSD. Enable SSH and set the hostname in the imager's advanced options so the boards come up headless and uniquely named.

node-01 — bash
rpi-imager --cli os.img /dev/sdaWriting... 100%ssh pi@node-01.localLinux node-01 6.6.20-v8+ aarch64

Tip

Give each node a memorable hostname (node-01…node-04) and a static DHCP lease on your router. Naming things well is half of operating them.

First boot, every node

Update, then enable cgroup memory — k3s needs it and the Pi disables it by default. Append the flags to the boot command line and reboot.

Forming the cluster

This is the moment four separate computers become one. k3s makes it almost anticlimactic: one command on the first node, one on each of the others.

  1. Install the server node

    Run the k3s installer on node-01. It comes up as a single-node cluster in seconds.

  2. Grab the join token

    Read /var/lib/rancher/k3s/server/node-token — the agents need it to authenticate.

  3. Join the workers

    Run the agent installer on the other three boards, pointing at the server's URL and token.

  4. Verify

    Four nodes, all Ready. You now have a Kubernetes cluster on your desk.

node-01 — k3s
kubectl get nodesnode-01   Ready   control-plane   148d   v1.29.4+k3s1node-02   Ready   <none>          148d   v1.29.4+k3s1node-03   Ready   <none>          148d   v1.29.4+k3s1node-04   Ready   <none>          148d   v1.29.4+k3s1

Watch out

Do not run the control plane and your storage on the same node without backups. If node-01 dies, you want its state on a volume you can re-mount, not a memory you can't recover.

The goal was never raw power. It was a machine that stops being a variable.

What I actually run

A homelab is only as good as the things it hosts. Mine earns its desk space with a small, boring, reliable set of services — boring being the highest compliment you can pay infrastructure.

The keepers

A bookmark archive, a feed reader, a personal Git remote, and this site's analytics. All stateless or backed by a single small database.

The experiments

A rotating cast of things I'm trying out — currently a self-hosted image CDN and a tiny status page. The cluster makes spinning these up cheap.

Deploying anything new is a single manifest and a kubectl apply. Press ↑ then Enter and the muscle memory does the rest. The whole point is that adding a service costs minutes, not an afternoon.

A quick glossary

k3s
A certified, lightweight Kubernetes distribution that fits comfortably on a Pi — all of the API, almost none of the bloat.
node
A single machine in the cluster. Here, one Raspberry Pi.
manifest
A YAML file describing the desired state of something you want running.

Was it worth it?

The honest answer: yes, but not for the reason I expected. The savings versus a VPS are real but slow. The real payoff is that the machine is legible — I understand every layer of it, and when something breaks I can actually fix it.

What I'd repeat

  • SSD boot — non-negotiable
  • Wired networking throughout
  • One power feed, labelled cables
  • k3s over full Kubernetes

What I'd skip

  • The RGB fans (noise, no benefit)
  • Overprovisioning to 4 nodes at once
  • Chasing 100% uptime obsessively
If you have been on the fence about a homelab, the Pi 4 is the gentlest possible on-ramp. Start with two boards; you will know within a weekend whether the bug has bitten. my note to a friend who asked
